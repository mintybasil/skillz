## Problem

Skills are critical for useful agents, but it's very hard to manage them across multiple deployments effectively. Agents will create skills locally or modify existing ones, and those changes need to reviewed and propagated accordingly.

Some external skill sources are not compatible with all agent harnesses, so we need to modify them, and then when changes are made upstream reflect those in the modified version. Also when dealing with external skill sources there are typically only a sub-set of the skills that we actually want to deploy.

## Goal
- Skills can be synchronized across all deployments
- Modifications to skills (including upstream updates) are done systematically and reviewed via Github pull requests

**Non-goals:**
- Writing skills from scratch
- Configuring agents to use the skills or deploying the skills to the agent environments

## Success Metric

The tool exists and is used to manage skills across deployments.

## Users

- **Primary:** Operator - manage multiple agent deployments and the associated skills

## Constraints / Assumptions

- **Constraints:**
	- External skills sources may vary in structure and whether they require modifications or not.
- **Assumptions:**
	- All deployments receive the same bundle of skills.
	- Upstream change detection is manual; the operator invokes updates when aware of upstream changes.
	- External skill sources are tracked as git submodules; the operator manages submodule refs manually (clone, update, commit ref changes).
	- Conflict resolution for modified external skills is handled through the 3-way merge process and PR review.

## Repo Layout

External skill sources are tracked as git submodules under a `sources/` directory. The bundle directory contains the final output — selected skills copied from submodules, plus locally-created skills.

```
repo/
├── .gitmodules                 # git submodule config (url + ref per source)
├── skills-manifest.yaml        # skill selections and modification metadata
├── sources/                    # git submodules — external skill sources
│   ├── hermes-skills/          # submodule for one external source
│   │   ├── devops/
│   │   │   ├── kanban-orchestrator/
│   │   │   └── kanban-worker/
│   │   ├── mlops/
│   │   │   └── ...
│   │   └── productivity/
│   │       └── notion/
│   └── hermes-agent-repo/      # another submodule
│       └── ...
└── skills/                     # the bundle — generated by the tool
    ├── hermes-skills/          # mirrors source name + category structure
    │   ├── devops/
    │   │   └── kanban-orchestrator/
    │   └── ...
    ├── hermes-agent-repo/
    │   └── ...
    └── mintybasil/             # all locally-created skills
        ├── my-custom-skill/
        └── another-local-skill/
```

Locally-created skills are not tracked in the manifest — they are all included automatically by virtue of being in the `mintybasil/` directory.

## Manifest Format

A single YAML file at the repo root (`skills-manifest.yaml`) tracking skill selections and modification metadata. Source URLs and refs are managed by git submodules (.gitmodules), so the manifest does not duplicate them.

```yaml
sources:
  - name: hermes-skills              # maps to submodule path sources/hermes-skills
    skills:
      - path: devops/kanban-orchestrator   # path within the source repo
        modified: false

      - path: mlops/inference/llama-cpp
        modified: true
        base_ref: v1.2.3              # upstream ref this modified version was based on
                                      # (used as merge base for 3-way merge on upstream updates)
        mod_tags: [hermes-compat]     # nature of modifications

      - path: productivity/notion
        modified: true
        base_ref: v1.1.0
        mod_tags: [hermes-compat, personalization]
```

Key fields:
- `base_ref`: Records which upstream version modifications were made against. Used as the merge base when upstream changes are pulled — the tool reconstructs the original file at this ref from the submodule's git history.
- `mod_tags`: Tags describing the nature of modifications applied to a skill. Valid values:
  - `hermes-compat` — modifications for Hermes agent harness compatibility (stripping incompatible tool calls, plugins, filenames, etc.)
  - `personalization` — modifications for the operator's own preferences or customizations

Locally-created skills are not listed in the manifest — all skills under the `mintybasil/` directory in the bundle are included automatically.

## Sync Workflow

The tool's primary operation is syncing the bundle from submodules + manifest. Two cases per skill:

**Unmodified skills:** Copied directly from the submodule into the bundle, overwriting any existing version. Always reflects the current submodule state.

**Modified skills:** When the submodule ref matches `base_ref`, the skill in the bundle is left untouched (it already has the operator's modifications applied at that base). When the submodule ref differs from `base_ref`, the tool performs a 3-way merge per file:

1. **base**: original file at `base_ref` (extracted from submodule git history via `git show base_ref:path/to/file`)
2. **ours**: modified version currently in the bundle
3. **theirs**: new upstream version from the current submodule state

The tool runs `git merge-file` for each file, writing the merged result (with conflict markers if any) back to the bundle. The operator then reviews, resolves conflicts manually, and updates `base_ref` in the manifest to the new submodule ref.

Edge cases:
- File added upstream, not in modified version: copied into the bundle
- File only in modified version (not upstream): kept as-is
- File deleted in modified version: left deleted (not re-added from upstream)

## User Stories

1. **Add a new external skill source:** Operator adds a git submodule under `sources/`, adds a source entry to the manifest with selected skill paths, runs sync, and opens a PR with the resulting changes.

2. **Select skills from an external source:** Operator edits the manifest to include/exclude specific skills from a source, re-syncs, and opens a PR.

3. **Modify an external skill for Hermes compatibility:** Operator runs sync (skill copied to bundle), modifies the skill in the bundle (stripping incompatible tool calls, plugins, filenames), marks it as `modified: true` with `base_ref` set to the current submodule ref and `mod_tags: [hermes-compat]` in the manifest, and opens a PR.

4. **Update when an upstream skill changes:** Operator updates the submodule ref (`git submodule update --remote`), runs sync. For modified skills, the tool 3-way merges upstream changes against the operator's modifications. Operator reviews merge results, resolves any conflicts, updates `base_ref` in the manifest to the new submodule ref, and opens a PR.

5. **Add a locally-created skill:** Operator adds the skill directory under `mintybasil/` in the bundle, and opens a PR. No manifest entry needed — local skills are included automatically.

6. **Personalize an external skill:** Operator modifies a skill in the bundle for their own preferences (not Hermes compatibility), marks it as `modified: true` with `mod_tags: [personalization]` and `base_ref` in the manifest, and opens a PR.

## Risks

- **Upstream restructuring:** External skill sources may reorganize their directory structure or change skill format, breaking the tracked paths and requiring manifest updates.
- **Source disappearance:** An external source repo may be deleted or made private, making future submodule updates impossible. Mitigation: the bundle directory and submodule cache preserve the last-synced version.
- **3-way merge conflicts:** When both upstream and local modifications change the same file, `git merge-file` will produce conflict markers requiring manual resolution. This is expected and handled by the PR review process, but could be tedious with heavily-modified skills that change frequently upstream.
- **Per-file merge limitation:** The 3-way merge operates per-file. Cross-file modifications (e.g., adding a reference file and linking to it from SKILL.md) won't be merged as a unit. Operator review of merged results is required.
- **Submodule ref drift:** If the operator updates a submodule ref but forgets to update `base_ref` in the manifest, the next sync will attempt an unnecessary merge. The tool should detect and warn about this.
- **No validation gate:** Invalid or incompatible skills could enter the bundle without being caught. Future enhancement.
